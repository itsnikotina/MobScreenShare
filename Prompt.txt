# 1. Objetivo do projeto

Estamos planejando um sistema privado de compartilhamento de tela para um pequeno grupo de amigos, integrado ao Discord.

A ideia é:

```text
┌──────────────────────┐
│ Windows Streamer App │
│                      │
│ • captura de tela    │
│ • captura de janela  │
│ • captura de áudio   │
│ • mixagem            │
│ • encode             │
│ • WebRTC publisher   │
└──────────┬───────────┘
           │
           │ P2P
           ▼
┌──────────────────────────────┐
│ Discord Activity             │
│                              │
│ GitHub Pages                 │
│                              │
│ • interface                  │
│ • Discord identity           │
│ • descoberta de streams      │
│ • WebRTC viewer              │
│ • reprodução de vídeo/áudio  │
└──────────────────────────────┘

              ▲
              │
              │ signaling
              │
       ┌──────┴──────┐
       │ Discord Bot │
       │             │
       │ • identity  │
       │ • rooms     │
       │ • signaling │
       │ • presence  │
       └─────────────┘
```

A regra fundamental é:

**O bot NÃO transporta vídeo ou áudio.**

O bot funciona apenas como uma espécie de "porteiro" / sinalizador:

* identifica usuários;
* identifica a sala;
* informa quem está transmitindo;
* informa quem quer assistir;
* troca informações necessárias para estabelecer WebRTC;
* mantém estado da sala;
* autentica/autoriza participantes.

Depois que a conexão WebRTC é estabelecida:

```text
Windows Streamer ═══════════════ Discord Activity
                    P2P
               vídeo + áudio
```

O bot não recebe mídia.

# 11. Topologia P2P

Nossa intenção é NÃO ter SFU/media server.

Exemplo:

```text
Streamer A
    │
    ├──────── Activity B
    │
    ├──────── Activity C
    │
    └──────── Activity D
```

Cada viewer cria uma conexão direta com o streamer.

Pesquise:

1. Escalabilidade desse modelo.
2. Número razoável de viewers para um pequeno grupo.
3. CPU/GPU do streamer.
4. Upload do streamer.
5. NAT.
6. CGNAT.
7. Firewalls.
8. STUN.
9. TURN.
10. Casos em que P2P não funciona.
11. Como detectar falha.
12. Como informar o usuário.

Não proponha SFU como requisito do MVP.

TURN pode ser discutido como possibilidade futura, mas atualmente queremos evitar relay de mídia.
